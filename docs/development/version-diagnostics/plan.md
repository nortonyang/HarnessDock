# HarnessDock 版本与诊断功能开发计划

## 目标

在原生 macOS 设置中增加“版本与诊断”页面，帮助普通用户确认应用、DeepSeek Harness 运行时和本机环境是否就绪，并能复制一份适合反馈问题的诊断摘要。

## 非目标

- 不实现自动更新或自动修复运行时。
- 不迁移 Windows / Electron 版本。
- 不收集或上传任何诊断信息。
- 不复制 API Key、Cookie、会话内容、完整工作区路径或 Harness 日志。

## 当前证据

- 应用已锁定 `@deepseek-ai/dsh@0.1.0-rc.6`，并优先复用本机 npx 缓存。
- 启动器已经区分“应用管理的服务”和“连接到已有服务”。
- 设置页已有 API 与余额、主题背景和语言三个入口，适合增加第四个诊断入口。
- 发布准备清单要求显示应用与上游运行时版本，以降低公开发布后的支持成本。

## 功能范围

1. 显示应用版本与构建号。
2. 显示锁定的 DeepSeek Harness 包版本。
3. 显示 macOS 版本与处理器架构。
4. 显示服务状态、连接方式和本地服务地址。
5. 显示当前工作区名称，不显示完整路径。
6. 检查 Node、npx 和已缓存 dsh 运行时是否可用。
7. 支持刷新状态和复制隐私安全的诊断摘要。

## 风险与处理

- **隐私泄露**：复制报告仅使用工作区末级名称；用户目录替换为 `~`；不读取密钥、Cookie、聊天和日志。
- **状态过时**：诊断页提供刷新按钮，并在页面出现时生成最新快照。
- **开发构建无版本号**：Bundle 缺少版本信息时显示 `Development`，不阻塞调试。
- **运行时扫描影响界面**：仅进入页面或主动刷新时检查，不在每次 SwiftUI 重绘时扫描。

## 开发阶段与原子用户故事

### 阶段 1：诊断数据

- 作为用户，我能看到当前应用、系统和 Harness 运行时的版本信息。
- 作为支持人员，我能得到一份不含敏感信息的稳定文本摘要。

### 阶段 2：设置界面

- 作为用户，我能从设置顶部切换到“版本与诊断”。
- 作为用户，我能刷新检查结果并一键复制摘要。
- 作为中英文用户，我能看到完整本地化文案。

### 阶段 3：验证

- 核心检查覆盖路径脱敏和报告字段。
- 静态检查、构建、签名与发布门禁保持通过。
- 实际启动应用，确认设置页布局、按钮和复制反馈正常。

## 验收标准

- 设置中出现“版本与诊断”入口，页面信息在窄窗口下不截断关键操作。
- 诊断报告不包含 API Key、完整工作区路径、Cookie、会话内容或日志正文。
- 用户目录路径以 `~` 脱敏；未找到的运行时有明确状态。
- 刷新和复制按钮可点击，复制后提供可见反馈。
- 中文和英文资源校验通过，应用成功构建并通过现有发布门禁。

## Gemini 开发交接

如需交给 Gemini 继续开发：只实现本计划定义的版本与诊断功能；复用现有 `AppModel`、`ExecutableLocator`、设置页面和本地化机制；不要新增遥测、网络请求、自动更新或密钥读取；完成后运行仓库已有检查与构建脚本。

## 完成后审计

- **改动文件**：新增 `HarnessDiagnostics` 核心快照；更新 `AppModel`、原生设置页、应用菜单、中英文文案、README、CHANGELOG 与发布审核。
- **验证结果**：核心检查、插件检查、交互静态检查、本地化校验、正式版构建、Info.plist 校验和代码签名校验通过；实际启动应用完成中文界面、四个设置入口、运行时状态和复制按钮验证。
- **已知限制**：Command Line Tools-only 环境缺少 Swift `Testing` 模块，无法直接执行现有 `swift test` 套件；框架无关的 `HarnessDockCoreChecks` 已覆盖本功能并通过。
- **后续建议**：发布前在干净 Mac 上验证“未安装 Node”“无 dsh 缓存”和 Intel / Universal 2 三种环境；诊断页当前不会自动修复缺失依赖。
